## 二、三个真实场景（设计依据）

**场景 A —— 游戏内一键放音效。**
游戏全屏，不想切窗口。队友在语音里。按 `F1` 放一段笑声（3 秒，单次），按 `F2` 放 BGM（循环，再按一次停）。全程不碰鼠标。

**场景 B —— 整首歌/mp4 转给队友。**
手里是 `xxx.mp4`（12 分钟）。拖进程序，点播放，声音从虚拟麦出去，抖音/B站的 BGM 队友听得见。需要进度条能拖、能暂停、能循环。播放时自己也能听见（可选）。

**场景 C —— 同时说话 + 游戏声。**
物理麦（我说话）+ 进程环回（游戏本音）+ 声板（音效）三路混在一起进虚拟线缆，队友全都听得到，三路音量独立。

这三条场景决定：**引擎必须常驻输出、源可以动态加减**，不能像现在这样「点开始才建线程」。

### 为什么删除「声板」页

「声板」和「播放器」都在做同一件事：选择一个音频并送进当前麦克风链路。
只把交互换成 pad 网格并不能形成独立领域，反而会产生两套文件、热键、播放状态、音量和停止逻辑。

最终只保留三页：

| 页 | 管什么 | 不管什么 |
|---|---|---|
| 路由 | 进程声、物理麦、输出设备、混音与开始/停止 | 音频文件库 |
| 音频库 | 分类树、音频列表、双击播放、暂停/停止、循环、播放进度 | 进程捕获配置 |
| 设置 | 设备、混音、全局热键、播放时按键、风险提示、虚拟线缆 | 日常音频选择 |

「音频库」同时承担 Soundpad 与播放器职责：短音效和长 MP4 都是列表中的音频项，
区别只体现在时长、循环和进度，不再拆成两个页面。

底部状态栏继续常驻。音频库只显示一个紧凑的「目标：当前输出设备」信息，不复制第二套设备状态。
双击音频时，声音发送到路由页当前选中的目标；所谓「指定麦克风」就是这个全局目标。

### 4.2 音频库

信息架构照你给的 Soundpad：左侧分类树，右侧当前分类的音频列表；不做 pad 网格。

```

│  │  └─ 各种小曲│ 3      一口气听完三十首合集         27:48     播放中    │
│  ├─ 游戏    0  │ 4      如假包换！大哥的小曲         5:07      待播放    │
│  │  ├─ mc    24│                                                       │
│  │  └─ 怪猎   3│                                                       │
│  ├─ 影视      │                                                       │
```

- 左侧是可折叠分类树：全部、未分类、自定义分类、导入文件夹；每项显示数量。
- 右侧是当前分类的列表：索引、音频名称、时长、播放状态。名称列不能撑大窗口，超长文本在列内省略。
- **双击音频名称立即播放**到当前全局目标；单击只选中；Enter 播放，Space 暂停/继续，Delete 删除或移出分类。
- 添加方式：添加文件、添加文件夹、拖放。文件夹可作为分类导入，也可以把已有文件拖到分类。
- WAV / MP3 / MP4 / M4A / FLAC / WMA 使用统一解码接口；MP4 只取音轨。
- 长音频和短音效使用同一列表模型，不再有「声板 pad」与「播放器文件」两套对象。
- 播放时按键**不是列表项属性**。它是全局播放行为，只在设置页配置一次。
- 音频库顶部只显示紧凑目标选择；它写入路由的同一个 `selected_device_id`，不复制设备状态。
- 底部是迷你播放条，不另建「当前播放器」卡片。

### 4.3 播放时按键（设置页，全局）

设置页只保留一行全局行为：

```
播放时按键     [不按键 ▼]   按键 [ F ] [更改]
               [播放开始按一次] / [播放期间一直按]
⚠ 启用后会向前台游戏发送键盘输入。部分反作弊可能拒绝或判定为可疑行为。
  默认关闭；工具与游戏应使用相同权限运行；停止播放、切换文件、异常退出都必须释放按键。
```

这行配置对音频库中所有音频生效：

| 模式 | 行为 |
|---|---|
| 不按键 | 只播放音频 |
| 按一次 | 播放开始时 `keydown → keyup` 一次 |
| 一直按 | 播放期间保持 `keydown`，结束/停止/切换时 `keyup` |

这样满足游戏 PTT：双击音频后自动开麦，不需要自己额外一直按热键。

## 六、播放模式与全局播放按键

音频库中的每个音频可以设置「单次 / 循环」；「按住 / 切换」属于触发控制，后续由全局热键或播放器控制实现，不再给每个 pad 单独做一套状态。

| 模式 | 行为 | 用途 |
|---|---|---|
| **单次** | 从头播放，结束自动停止 | 短音效，默认 |
| **循环** | 播放结束后回到开头 | BGM / 环境音 |

全局「播放时按键」另有三种：

| 模式 | 行为 |
|---|---|
| 不按键 | 只播放音频 |
| 播放开始按一次 | `keydown → keyup` 一次，用于触发游戏 PTT |
| 播放期间一直按 | 开始 `keydown`，结束/停止/切换时 `keyup` |

细节约定：

- **淡入/淡出 15 ms**，防止起停 click。
- 双击列表项时，播放到当前全局目标；停止、切换和异常结束都必须清理 Hold 按键。
- 触发到出声目标 **< 50 ms**；不做低延迟独占模式。
- 采样率与设备不同，用现有线性插值重采样。
`src/hotkey.rs` 用 `RegisterHotKey`，一个组合、一个开关动作（开始/停止转发）。够用，但撑不起声板。

### 7.2 两套方案

| | 方案 A：`RegisterHotKey` | 方案 B：低级钩子 `WH_KEYBOARD_LL` + `WH_MOUSE_LL` |
|---|---|---|
| 按住（keydown/keyup） | ✗ 只有按下 | ✓ |
| 鼠标侧键 | ✗ | ✓ |
| 独占键（游戏收不到） | 天然独占（会吞键） | 可选，默认放行 |
| 支持多绑定 | ✓（每绑定一个 id） | ✓（自己比对） |
| 对系统输入路径的影响 | 无 | 有：每次按键都过我们的回调，回调必须极快 |
| 反作弊观感 | 无 | 部分游戏的反作弊可能把全局键盘钩子当可疑行为 |
| 权限边界 | 无 | 工具与游戏不同权限（如游戏以管理员跑）时可能收不到 |

**已定：两套都做，设置页里三档切换** —— `仅系统热键`（`RegisterHotKey`）/ `全局钩子`（`WH_KEYBOARD_LL` + `WH_MOUSE_LL`）/ `关闭`。**默认 `仅系统热键`**；切到 `全局钩子` 时当场弹出风险提示（文案见 4.4）。理由：你要「一次 / 一直 / 按住」，A 做不到；Soundpad 类工具普遍是 B，但 B 有反作弊观感与系统输入路径成本，这个风险必须由用户自己选，而不是我替他默认打开。

三档的能力差异：

| 能力 | 仅系统热键 | 全局钩子 | 关闭 |
|---|---|---|---|
| 单次 / 循环 / 切换 | ✓ | ✓ | ✗ |
| 按住（松开停） | ✗ | ✓ | ✗ |
| 鼠标侧键 | ✗ | ✓ | ✗ |
| 独占键（游戏收不到） | 天然独占 | 可选 | ✗ |
| 对系统输入路径有影响 | 无 | 有 | 无 |
| 反作弊观感 | 无 | 有 | 无 |

全局钩子模式的实现约束（写进代码规范）：

1. 钩子回调只做一件事：`PostMessageW` 到自己的消息窗口。**绝不**在回调里判断文件、读盘、加锁、打日志。
2. 回调超时会**被系统静默摘掉钩子**（系统默认阈值为数百毫秒），所以回调必须是常数时间。
3. 只比对已注册的绑定键，**不记录、不落盘、不上报**任何其它按键。
4. 三档切换在设置页（`仅系统热键` / `全局钩子` / `关闭`）。切到 `全局钩子` 时显示风险提示；关掉后立即 `UnhookWindowsHookEx`，不留残留钩子。
5. 钩子线程复用现有消息窗口线程（`hotkey.rs` 已有 `GetMessageW` 循环），不另起线程。
6. 忽略 `LLKHF_INJECTED` 事件，避免被模拟输入误触发。

### 7.3 捕获与冲突

- 点「更改」→ 进入捕获 → 按任意键（含鼠标侧键）→ 显示组合 → **立刻试注册**，被别人占用或与自家其它绑定冲突时当场标红提示「这个键已被占用 / 已绑定给 笑」。
- 捕获界面按 `Esc` 取消。
- 默认绑定：
  - 开始/停止转发：`Ctrl+Shift+F8`（沿用现有）
  - 停止全部声音：未设置
  - pad：F1…F12 按顺序自动分配
- 冲突判定不只看能否注册成功：`RegisterHotKey` 失败才说明被外部占用，但用户自己重复绑同一键必须在**我们自己**这里挡住。

## 八、音频架构改动（本次重构的技术核心）

### 8.1 现状的问题

`AudioEngine::start(pid, device, mic)` 一次性建好「捕获线程 + 麦线程 + 渲染线程」，停止时全拆。**声板做不到**：pad 是随时按随时播的，不能每次都重建 WASAPI 流。

### 8.2 新结构

```
UI 线程（Slint）
   │  命令：OpenOutput / CloseOutput / SetRoute(pid) / SetMic(id) /
   │        PadTrigger(i) / PadStop(i) / StopAll / FilePlay(path) / SetVolume(kind)
   ▼
AudioEngine（安全 API，不含 unsafe）
   ├─ render 线程（常驻，打开输出后一直跑）
   │      pop(ring_process) + pop(ring_mic) + pop(ring_sfx) → 总线音量 → 写设备
   ├─ capture 线程（跟随 SetRoute 动态起停）  → ring_process
   ├─ mic 线程（跟随 SetMic 动态起停）        → ring_mic
   └─ sfx 线程（跟随 OpenOutput 起停）        → ring_sfx   ← 新增
         内部：pad 播放状态机 + 文件播放器 + 重采样 + 淡入淡出
```

关键改动只有三点：

1. **输出常驻**：`OpenOutput(device)` 建 render 线程，空闲时写静音；`CloseOutput` 才拆。开始/停止按钮 = Open/Close。
2. **源可动态加减**：进程环回、物理麦各自持有自己的线程，随时起停，不影响别人。
3. **新增第三条 ring `ring_sfx`**：所有音效与文件播放的混音结果在这条 ring 上，由**单个** sfx 线程生产。

### 8.3 为什么是「三条固定 ring」而不是「动态源列表」

`SpscRing` 的契约是**单生产者单消费者**（`src/audio/buffer.rs`）。动态注册 N 个源会破坏这个契约，逼出锁或者更复杂的无锁结构。

三条固定 ring 的收益：

- render 侧只是多一次 `pop` + 一次加法，热路径无锁、无分配。
- 多个 pad 的混音发生在 **sfx 线程内部**（本来就是单线程），直接数组加法，零同步成本。
- 和现有 `ring` + `mic_ring` 的写法一致，不是新范式。

代价：pad 与播放器共用一条 `sfx` 音量通道（不能给每个 pad 单独的总线音量——pad 各自音量在混合前乘，没问题）。

### 8.4 sfx 线程怎么做

- 定时器驱动，块大小 10 ms（`recv_timeout` + `try_recv` 排空命令队列）。
- 每轮：处理命令 → 对每个活跃 pad 从解码缓冲取一块 → 乘各自音量 → 求和 → 淡入淡出斜坡 → `push_latest` 到 ring。
- 命令通道用 `Mutex<VecDeque<Cmd>>` + `try_lock`。低频（每次按键一次），且**绝不在锁内做解码/读盘**。ring 容量约 200 ms，吸收定时器抖动。
- 没有活跃源时不分配、不计算，直接推静音。
- 实时约束沿用现状：无 `unwrap`/`panic`、不刷日志、不扩容。

### 8.5 关停

沿用现有约定：`AtomicBool` + 等待超时 50–100 ms，`Drop` 里 `join`。切换输出设备 = Close + Open，会有约 100 ms 静音，属正常。

## 九、解码方案（mp4 怎么读）

### 9.1 约束

WASAPI 只吃 PCM，所以「把 mp4 直接交给音频 API」这件事不存在，必须有解码器。`goal.md` 第十二节与 AGENTS.md 都硬禁止 FFmpeg / GStreamer。

### 9.2 三条路对比（你问的「允许 FFmpeg 会不会更简单」）

| | Media Foundation（本方案） | Symphonia（纯 Rust） | FFmpeg |
|---|---|---|---|
| 形态 | Windows 内置 API | 静态链接进 exe | 随程序分发 `avcodec-*.dll` / `avformat-*.dll` / `avutil-*.dll` / `swresample-*.dll` |
| 磁盘占用 | **0**（系统自带） | exe 增大（量级估计 +0.5–2 MB，S5 实测后回填） | 预编译包**不能按 codec 裁剪**：BtbN master x64 的 LGPL shared zip 已 73.5 MiB、LGPL static zip 164.2 MiB；gyan.dev essentials static 7z 34 MB。想只留音频解码必须自己 `--disable-everything` 编一份（估计落到 +1.5–3 MB），但仍要背 MSYS2 + nasm 工具链与 LGPL 义务 |
| 内存 | 解码器 MFT 加载后约几 MB（懒加载） | 与 FFmpeg 同量级 | 与 MF 同量级 |
| 格式覆盖 | mp3 / AAC(mp4,m4a) / WMA / FLAC / ALAC / WAV / ADPCM | mp4(AAC-LC)、mp3、flac、wav、ogg/vorbis、mkv/webm、alac；**无 WMA**，**Opus 未实现** | 最全（Opus、WMA、任何容器） |
| 依赖与部署 | 无新 crate；Windows N 版需装 Media Feature Pack | 新增 6–7 个 crate；无系统依赖 | 需要管理 FFmpeg 构建产物的分发与许可，或自己用 MSVC + nasm 编一份裁剪版 |
| 许可 | 系统组件 | MPL-2.0（文件级 copyleft，链接无碍） | LGPL 需动态链接 + 声明；GPL 构建会传染 |
| 与「小、快、稳、原生」 | 最贴 | 次之 | 最差 |

**结论：允许 FFmpeg 也不会更简单，反而更重。** 它的「简单」只在那种自带二进制包的封装 crate 里成立；落到这个项目上，要么随程序背几个 DLL（磁盘占用从当前 10.1 MB 变成几十 MB，与 `docs/step-09-performance.md` 定的取向正面冲突），要么自己搭 MSVC + nasm 工具链编译一份裁剪版 FFmpeg——成本远高于写一遍 MF 调用。

你担心的「MF 依赖系统媒体功能」是真问题，但正确答案是 symphonia（纯 Rust、零系统依赖），不是 FFmpeg。

**所以解码定案：MF 为唯一实现，`MFSTARTUP` 懒加载；不预先做双后端抽象。** `src/audio/decode.rs` 内部接口只有「打开 / 读一块 / seek / 关闭」，真遇到 Windows N 版没装媒体功能包、或需要 Opus 的场合，换 symphonia 只动这一个文件，不动上层。FFmpeg 保持禁用。

### 9.3 格式覆盖

| 格式 | 方案 |
|---|---|
| WAV（PCM / IEEE float） | **自写解析器**（无依赖，几十行，可控） |
| mp3 / mp4 / m4a(AAC) / flac / wma | **Media Foundation `IMFSourceReader`**（Windows 内置） |
| ogg / opus / webm 音轨 | **不支持**（系统没内置解码器）。错误短句写清楚；真要就换 symphonia 后端 |

Media Foundation 是系统 API，不需要新第三方 crate，代价只是 `windows` 的 feature 列表加一个 `Win32_Media_MediaFoundation`。

### 9.4 实现规格（S5 照此落地）

**模块**：`src/audio/decode.rs`，唯一放 MF `unsafe` 的地方。对外一个类型，WAV 与 MF 都是它的内部变体，上层与格式无关：

```rust
pub struct MediaInfo { pub duration_hns: u64, pub sample_rate: u32, pub channels: u16 }

pub struct AudioReader { /* Wav | Mf */ }

impl AudioReader {
    /// 按扩展名/魔数选后端。
    pub fn open(path: &Path) -> Result<Self, Error>;
    pub fn info(&self) -> MediaInfo;
    pub fn seek_hns(&mut self, hns: u64) -> Result<(), Error>;
    /// 读一块交错 f32 到 dst（先清空）。返回 0 表示到结尾。
    pub fn read_block(&mut self, dst: &mut Vec<f32>) -> Result<usize, Error>;
}
```

不做 trait object、不做双后端开关：就一个 enum 两个变体。将来若要换 symphonia，只换 MF 那个变体的内部。

**初始化（懒加载）**

- 进程级 `OnceLock`：第一次 `AudioReader::open` 时才 `MFStartup(MF_VERSION, MFSTARTUP_LITE)`（`MFSTARTUP_LITE` 关掉 socket 栈，本地文件够用）。不主动 `MFShutdown`，随进程退出。
- 每个碰 MF 的线程各自 `CoInitializeEx(COINIT_MULTITHREADED)`：UI 线程已有（`com::init_mta`），sfx 线程启动时调一次。
- `Cargo.toml` 的 `windows` features 加一项 `Win32_Media_MediaFoundation`（`PROPVARIANT` 要的 `Win32_System_Variant` 已在）。

**打开（调用序列）**

1. `MFCreateSourceReaderFromURL` 打开文件。
2. 先 `SetStreamSelection(MF_SOURCE_READER_ALL_STREAMS, FALSE)`，再 `SetStreamSelection(MF_SOURCE_READER_FIRST_AUDIO_STREAM, TRUE)`。目的：**mp4 的视频轨绝不能被解码**。该组合若被某个容器拒绝，退化为「`ReadSample` 只传音频流索引、其余流一律不触碰」。
3. 构造**部分媒体类型**：`MF_MT_MAJOR_TYPE = MFMediaType_Audio`、`MF_MT_SUBTYPE = MFAudioFormat_Float`（交错 f32）、`MF_MT_ALL_SAMPLES_INDEPENDENT = TRUE` → `SetCurrentMediaType(MF_SOURCE_READER_FIRST_AUDIO_STREAM, …)`。`ALL_SAMPLES_INDEPENDENT` 不设会 `E_INVALIDARG`（与已知陷阱表里 `0x80070057` 同一类坑）。
4. **故意不指定采样率与声道**：MF 直接给解码器的原生输出格式；采样率/声道对齐交给已有的 `audio/format.rs::Converter`（线性插值）。这样既不引入 MF 自带重采样器，上层也只有一个可变量。
5. `GetCurrentMediaType` 读回 `MF_MT_AUDIO_SAMPLES_PER_SECOND` / `MF_MT_AUDIO_NUM_CHANNELS`，作为本文件的 `AudioFormat`。
6. `GetPresentationAttribute(MF_SOURCE_READER_MEDIASOURCE, MF_PD_DURATION)` 拿时长（100 ns 单位）给进度条。

**读取与缓冲（全部在 sfx 线程）**

- 每个活跃播放器一个 `Vec<f32>` 解码缓冲，容量 1 秒（原生 48 kHz 立体声约 384 KB）。
- sfx 每 10 ms 一个 tick：`buffered < 200 ms` 就 `ReadSample` 补 200 ms。**不另起解码线程、不加锁**——MP3/AAC 解 200 ms 只要几毫秒。
- `ring_sfx` 约 200 ms 容量吸收定时器抖动；解码缓冲 + ring 双层吸收文件 I/O 抖动，不会直接顶到 WASAPI。
- 出 ring 前照旧过 `Converter`（原生 → 设备混音格式），和捕获侧是同一条路径、同一套代码。

**seek / 循环 / 进度**

- seek：`SetCurrentPosition(GUID_NULL, PROPVARIANT VT_I8 = hns)`。AAC 帧粒度约 21 ms、MP3 约 26 ms，拖动进度条够用。
- 进度：按「累计产出的原生帧数 ÷ 原生采样率」算，**不依赖 `ReadSample` 的时间戳**（seek 后不需要额外校正）。
- 循环：`read_block` 返回 0（EOF）时，勾了循环就 seek 回 0 继续，否则走淡出停止。
- 淡入/淡出与 pad 共用同一套 15 ms 斜坡，路径只有一条。

**错误映射**（细节进 `tracing`，界面只出短句）

| 情况 | 界面短句 |
|---|---|
| 文件不存在 / 被占用 / 打不开 | 无法打开文件 |
| 没有音频流（纯视频 mp4） | 这个文件里没有声音轨道 |
| 格式系统不支持（含 Windows N 版缺媒体功能包） | 不支持的音频格式 |
| 解码中途失败 | 解码失败 |

新增 `Error::Decode(&'static str)` 承载以上分支。

**明确不做**

- 不解码视频、不取封面、不做字幕。
- 不整曲预解码进内存（3 分钟 44.1 kHz 立体声 f32 = 63 MB，违反 `docs/step-09-performance.md` 定的取向）。
- 不做 gapless 精确拼接；倍速是 P2。
- 不启用 `MF_SOURCE_READER_ENABLE_AUDIO_PROCESSING`（那是 MF 自带重采样/处理链，我们用不上）。

**S5 要实测并回填本文档的两项**：首次播放的 `MFStartup` 延迟、文件播放期间的常驻内存增量。

### 9.5 明确不做与备选

| 方案 | 结论 |
|---|---|
| FFmpeg / GStreamer | **不做**（`goal.md` 第十二节 + AGENTS.md 禁止；重量理由见 9.2） |
| 自己写 mp3/AAC 解码器 | 不做。成本与正确性风险远超收益 |
| `mciSendString` 播放 | 不做。拿不到 PCM，混不进 ring，延迟不可控 |
| WMP COM / `IWMPPlayer` | 不做。同样拿不到可混音的数据 |
| 只支持 WAV | 不做。你要的就是 mp4 |
| Symphonia | **备选**，保留为解码后端的替换实现，不在本期落地 |

## 十三、风险与边界

| 风险 | 说明 | 应对 |
|---|---|---|
| 全局键盘钩子被反作弊拦 | 部分竞技游戏的反作弊会关注全局键鼠钩子。DRG 无内核反作弊，但你以后可能换游戏 | 设置页可一键停用钩子（退回 `RegisterHotKey` 模式）；不注入 DLL；只读键码不做任何上报 |
| 钩子回调拖慢系统输入 | 回调超时会被系统摘钩子 | 回调只 `PostMessage`，常数时间；加静态断言式的代码评审规则 |
| 工具与游戏权限不一致 | 游戏以管理员运行时，热键可能收不到 | 文档写明：与游戏同权限运行（都提权或都不提权） |
| MF 常驻内存 | 解码器 DLL 加载后不会走 | 懒加载；S6 实测并记录数字，超预算就考虑「停止播放后 `MFShutdown`」 |
| 格式覆盖 | ogg/opus/webm 音轨不支持 | UI 明确错误短句，不静默失败 |
| 输出设备切换有 100 ms 静音 | 重建 WASAPI 流 | 可接受，不为此上独占模式 |
| 功能变多 = 变复杂 | 与「不要太复杂」背离 | 高级项（独占键、仅前台生效、托盘、开机启动）默认关且折叠在设置页 |
| 多实例抢资源 | 两个进程抢热键/设备 | P0 单实例互斥 |

## 十六、验收方式

沿用 AGENTS.md 第五节的规矩，每片结束必须真跑，`cargo check` 不算：

1. `scripts\build-dev.cmd build`（release 只在 S7）。
2. 起 UI，实际操作刚改的路径（选进程 → 选设备 → 开始 → 目标设备有声 → 音量有效 → 停止即停）。
3. 音频库：左侧分类树 → 右侧双击真实 WAV/MP4 → 当前虚拟麦有声；循环、停止、列表切换。
4. 播放时按键：设置为 Press/Hold → 播放音频 → 验证按键动作与停止时释放；默认 None 不注入。
5. 试听：打开监听，本机扬声器能听到同一路声音；关掉立即停。
6. 错误路径：进程退出、设备拔出、无音轨 mp4、被占用的热键、切到全局钩子后停用钩子。
7. S7 记录实测：空闲/播放 RAM、CPU、启动时间、release 体积（对比 `docs/step-09-performance.md` 的 10.1 MB / 92 ms 基线）。
